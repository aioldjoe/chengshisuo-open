# STT 測試集（issue #28）

`pnpm bakeoff:stt` 吃的就是這個資料夾。一場 case 一個子資料夾：

```
bakeoff/cases/
  far-field/
    case.json          # 這場是什麼、詞表、人工標註
    audio.m4a          # 音檔（也可以在 case.json 指到外部路徑）
    reference.md       # 人工校對過的正確稿子 ← 這張票的主要成本
```

**只有這份 README 與 `_example/` 進版控**——其餘是真實會議內容，`.gitignore` 擋著。

## 為什麼需要這個資料夾

2026-08-12 的 Scribe 選型只驗過**一場**安靜會議室、麥克風在桌上的理想錄音，判準是
「讀起來對不對」，沒有任何數字。真實使用者是拿手機放在會議桌角落錄的。

STT 是整條 pipeline 的天花板：聽錯了，校正與抽取只會把錯的東西整理得更整齊、更有說服力。
講者分離的錯更貴——校正 pass 完全不碰它，而記錄頁的說話人命名（#23）會把錯的歸屬**固化成真名**。

沒有 reference 就沒有分數；沒有分數，「吵一點會不會塌」只能用印象回答。

## 場景清單（每類至少一場、8–15 分鐘）

| id 建議 | 場景 | 要驗的是 |
|---|---|---|
| `quiet-room` | 安靜會議室、多人、桌上收音 | baseline（＝2026-08-12 那場） |
| `noisy` | 背景噪音：冷氣／施工／咖啡廳 | 訊噪比掉下去會塌成什麼樣 |
| `far-field` | 手機放桌角，離講者 2 公尺以上 | **真實使用者的錄法** |
| `crosstalk` | 多人插話搶話 | 講者分離最可能塌的地方 |
| `jargon` | 大量專有名詞與中英夾雜 | ＝我們的主客群 |
| `online` | 線上會議：喇叭回放＋壓縮音質 | 二次編碼後的音質 |

**先做 2–3 類把流程跑通，不要一次備齊六類再開始。** 人工 reference 是這張票的主要成本。

## 做一場 case 的步驟

**1. 建資料夾與 `case.json`**（照抄 `_example/case.json`）

```jsonc
{
  "scenario": "遠場：手機放桌角，離講者 2 公尺",
  "audio": "audio.m4a",        // 相對於這個資料夾，或絕對路徑、或 ~/...
  "speakers": 4,               // 真正的講者數（沒填就不跑「講者數提示」那組）
  "audioSeconds": 900,         // 選填；沒填就用引擎回報的長度
  "terms": ["一次側變流量", "IPLV", "建築能效"],
  "anchors": [{ "at": "03:12", "text": "先講泵浦的部分" }],
  "silences": [{ "from": "05:10", "to": "05:40" }],
  "notes": "冷氣正下方、iPhone 語音備忘錄"
}
```

- **`terms`**：這場真正出現的專有名詞。**這條比 CER 更貼近產品**——CER 5% 但把公司名全聽錯的稿子是廢的。
- **`anchors`**：三五句「這句話真的在第幾秒」，自己拉播放器對一下就好。
  為什麼不拿 reference 的時間戳比：reference 是改引擎輸出改出來的，時間戳本來就是那家引擎的，比了等於比自己。
- **`silences`**：會議空檔（沒人講話）的區間。**幻覺補字最容易發生在這裡，而且補出來的句子完全通順**，
  人工抽查不見得看得出來——只有對著空檔看才抓得到。標一兩段就有用。

**2. 產 reference 草稿**

```bash
pnpm bakeoff:stt --init far-field
```

出來的是 `reference.draft.md`。**reference 不是從零打字，是拿引擎輸出來改**——這是把成本壓到可承受的唯一辦法。

**3. 人工校對**（一場 8–15 分鐘的音檔大約要 1–2 小時）

聽著音檔一句一句改，只改兩件事：

- **聽錯的字**——改成他真正講的那個詞。
- **講者歸屬**——這段是不是這個人講的；切錯人的地方要把段落切開、標對人。
  **切開時順手把新段落的時間戳改對**（拉播放器看一眼就好）——講者邊界與歸屬的分數
  是拿 reference 的時間戳算的，不改的話等於沿用引擎切錯的那個時間點。

**不要順稿、不要補標點、不要改說法。** 逐字稿的規矩是還原語氣：在地化、潤飾、清口吃一律不做
（見 `lib/pipeline/correct.ts`）。reference 若被順過，量到的就不是「聽錯」而是「講得不夠漂亮」。
標點與空白不影響分數（比對前會正規化掉），改不改都行。

改完**把檔名改成 `reference.md`**。`--init` 只寫 `.draft.md`，不會蓋掉人改了兩小時的東西。

**4. 跑**

```bash
pnpm bakeoff:stt                      # 每一場 × 每一家
pnpm bakeoff:stt --case far-field     # 只跑一場
pnpm bakeoff:stt --engines scribe,scribe-v2
pnpm bakeoff:stt --fresh              # 不吃快取、重打 API（要花錢）
pnpm bakeoff:stt --no-correct         # 不跑校正 pass 的增益比較
```

轉寫結果會快取在 `bakeoff/results/stt-cache/`，**改指標重算不用重打 API**。
產出在 `bakeoff/results/stt-summary.md`（總表）與 `stt-<case>.md`（每場的細節）。

### reference 的時間戳有個先天偏差，讀表時要記得

草稿是某一家出的，**時間戳原封不動就是那一家的**。所以「邊界誤差」「歸屬正確率」
對出草稿的那一家系統性有利——它是在跟自己比。三個辦法，挑一個：

1. 只看**相對差距**，別看絕對值（大家都跟同一家比，至少偏差方向一致）。
2. 人工校對時把切開的段落重新計時（上面那條）。
3. 文字類指標（CER、詞表召回、空檔補字、重複）**不受這個偏差影響**，跨引擎可以直接比。

## 對戰名單

`scribe`（v1、現況）、`scribe-v2`、`scribe-keyterms`（v1 ＋ 把 `terms` 當提示詞餵進 STT）、
`scribe-speakers`（v1 ＋ 講者數提示）、`openai`（gpt-4o-transcribe-diarize，第二供應商對照組）。

**`scribe-keyterms` 是帶著答案考試**：餵進去的 keyterms 就是拿來算召回率的那份詞表，
它的召回率不能跟別組並排比。真實情境沒有逐場詞表——要讓它上線得先回答「詞表從哪來」
（使用者自己填？從歷史會議累積？），那是另一張票。看它有沒有用要看 CER 與逐段表。
名單在 `bakeoff/stt-engines.ts`，要加一組就加一行。

Scribe 那幾組跑的是產品自己那支 `lib/stt/scribe.ts`——量到的必須是使用者真的拿到的東西。

金鑰缺哪家就跳過哪家（不是失敗）：Scribe 吃 `.env.local` 的 `ELEVENLABS_API_KEY`，
對照組吃 `OPENAI_API_KEY`（產品用不到這把，只有 bake-off 要）。

## 讀表

- **CER**：字元錯誤率。繁中不用 WER，中文沒有詞邊界，斷詞本身就會引入誤差。
- **長度比** > 1 是補字（幻覺的宏觀跡象），< 1 是漏字。
- **詞表召回**：命中幾個。細節表還會列**同一個詞被聽成幾種寫法**——
  `applyCorrections` 是逐字替換，三種寫法就要三條 correction，**錯誤有多發散直接決定校正 pass 補得回多少**。
- **講者數**（hyp/ref）、**邊界誤差**（跳播準不準）、**歸屬正確率**（簡化版，非完整 DER）。
- **輪替／亂切**：講者切換次數 hyp/ref，以及附近沒有任何 ref 邊界的 hyp 邊界佔比。
  **邊界誤差一定要跟這兩欄一起讀**——每兩秒亂切一刀的分離，邊界誤差會漂亮地接近 0 秒。
- **塌得最兇的三段**：逐段 CER 的粗略定位。「哪一類場景會塌」的答案常常是
  「只有離麥克風最遠的那個人講話的那五分鐘塌了」，全篇平均看不出來。
- **校正增益**：同一份稿子校正前後。CER 幾乎不動是正常的（只換詞不重寫），**要看詞表召回補回多少**；
  **CER 變差就是警訊**——校正動到了不該動的地方。

## 這張票的判準

跑完要能明確回答兩個問題：**哪一類場景會塌**，以及**塌的是文字還是講者**。
結論（含「哪種錄音方式我們其實撐不住」）回寫進 `CLAUDE.md` 或 `docs/`——
那會直接影響要不要在產品裡教使用者怎麼錄。

**不在這張票換供應商。先量到，再決定。**
